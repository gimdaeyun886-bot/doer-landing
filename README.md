# Do-er

**배포 URL:** https://doer-mission8.vercel.app (열면 바로 앱 로그인 화면으로 갑니다. 소개 페이지는 따로 열지 않습니다.)

**고도화 기능:** OpenAI API 활용 — [놓친 날 이어 가기](#고도화-놓친-날-이어-가기)

## 서비스 소개

Do-er는 해야 할 일을 정해 놓고도 휴대폰 때문에 시작을 미루는 사람을 위한 AI 실행 코치입니다. 자격시험, 어학, 운동, 독서, 포트폴리오처럼 목표가 있고 매일 조금씩 해야 하는 일이면 모두 대상입니다.

1. **계획**: 코치(AI)와 대화하며 목표와 사정을 말하면, 끝나는 날까지의 날짜별 계획을 짜고 계획을 그렇게 짠 근거를 보여 줍니다.
2. **잠금**: 오늘 할 일을 시작하면, 사용자가 직접 고른 앱이나 화면(릴스, 쇼츠 등)이 잠깁니다. 전화, 메신저, 검색은 잠그지 않습니다.
3. **맞춤 인증**: 과제마다 AI가 맞는 인증 방식(사진, 퀴즈, 글)을 골라 두고, 끝낸 것을 인증하면 잠금이 풀립니다.
4. **조정**: 잠금을 바로 푸는 길은 없습니다. 버거운 날은 코치와 대화해 조정안과 그 대가를 보고 고릅니다.

웹 앱(이 저장소의 Next.js 부분)이 서비스의 전부를 담고, 안드로이드 앱(`android/`)은 웹 화면을 띄우고 실제 앱 잠금만 맡는 얇은 껍데기입니다. **확인 대상은 웹 앱**이며, 브라우저만으로 잠금을 뺀 모든 기능을 확인할 수 있습니다. 안드로이드 앱은 빌드 산출물이라 저장소에 넣지 않았습니다.

### 평가 안내

- **가입해서 씁니다.** 배포 URL에서 "시작하기"를 누르고 이메일로 가입하면 메일 확인 없이 바로 쓸 수 있습니다. 실제 개인정보 대신 아무 이메일 형식이나 써도 됩니다. 데이터는 로그인한 사람 것만 보입니다(Supabase RLS).
- **CRUD 한 사이클**: 코치 탭에서 목표를 말하고 확인 장에서 "계획 만들기"(등록) → 목표 탭(목록) → 목표 하나(상세) → "목표 고치기"(수정, 자료 사진 올리기) → 오른쪽 위 휴지통(삭제. 휴지통에 30일 두고 되살리거나 바로 지울 수 있음).
- 등록에는 AI가 계획을 짜는 1분쯤이 걸립니다. AI 사용량은 사람마다 하루 횟수와 주간 금액으로 제한돼 있습니다.

## 고도화: 놓친 날 이어 가기

**고른 축: OpenAI API 활용 기능.**

### 어떤 한계를 메우나

지금까지는 할 일을 하루 놓치면 기록에 "못 함"이 찍히고 연속 기록이 끊길 뿐이었습니다. 못 한 분량을 다시 배치할 길이 없어서, 계획은 조용히 어긋나고 사용자는 다음 날 무엇을 해야 할지 모른 채 돌아옵니다. 테스터 한 주 동안 거의 반드시 생기는 상황이고, 목표 종류나 인증 방식과 관계없이 생깁니다.

한 번 놓친 것 자체는 습관 형성을 크게 해치지 않지만, "끊겼다"고 보여 주면 다음 참여가 줄고 고칠 길을 주면 그 감소가 줄어든다는 연구가 있습니다(Lally 외 2010, Silverman & Barasch 2023). 그래서 놓친 날을 나무라는 대신 이어 갈 길을 보여 주되, 대가 없이 기록만 살려 주지는 않도록 했습니다.

### 흐름 (언제, 무엇을 넣고, 무엇이 나오나)

1. **언제:** 오늘 화면을 열었을 때 최근 3일 안에 인증하지 못한 할 일이 있고 아직 정리하지 않았으면, 목록 위에 "어제 못 한 일 2가지가 있어요" 한 줄이 보입니다.
2. **입력:** 줄을 누르면 코치가 놓친 일을 먼저 말하고 사정을 묻습니다. "바빴어요" 같은 버튼을 누르거나 직접 적고, 말하지 않고 넘어갈 수도 있습니다. 놓친 일 목록은 서버가 계획과 인증 기록으로 계산하고, 브라우저가 보낸 값은 쓰지 않습니다.
3. **처리:** 서버가 기본안 두 가지를 코드로 만듭니다. "남은 날에 나눠 하기"는 앞으로 7일 중 쉬는 날이 아닌 날에 하나씩 넣고, "이번엔 넘기기"는 다시 하지 않습니다. 사정을 말했으면 AI가 "놓친 것 중 무엇을 살릴지"를 골라 안을 1~2개 더합니다. 예: 시험이 가까우면 모의고사는 살리고 복습은 넘기기.
4. **결과:** 고르기 전에는 아무것도 바뀌지 않습니다. 고르면 서버가 안을 다시 검사한 뒤, 옮길 일의 사본을 받는 날의 계획에 더합니다. 사본에는 "화요일에서 옮겨 옴"이 붙습니다. 정리 기록은 `adjustments`에 `kind='recover'`로 남고, 오늘 화면의 줄은 사라집니다.
5. **기록:** 지난 날의 계획은 그대로 두므로 그날은 여전히 "못 함"입니다. 놓친 일을 모두 옮겼고 옮긴 사본을 모두 인증하면, 그때 그날이 "조정"으로 바뀌고 연속 기록이 이어집니다. 넘기기를 고르면 기록은 바뀌지 않습니다.

### 지키는 규칙 (코드가 정하고 AI는 따르기만 함)

| 규칙 | 이유 | 어디서 |
|---|---|---|
| 넘기기는 기록을 살리지 않음 | 빼기만 해도 연속 기록이 이어지면 대가 없는 해제와 같다 | `lib/streak.ts` |
| 기록을 되살리는 정리는 7일에 한 번 | 매일 미루기를 막는다 | `lib/recover.ts` `canRepair` |
| 옮긴 일은 다시 옮기지 않음 (조정에서도) | 미루기를 되풀이하지 않게 | `findMissed`, `applyAdjustment` |
| 받는 날은 원래 분량(또는 하루 시간)의 두 배까지, 쉬는 날·계획 밖은 안 됨 | 몰아 넣으면 다음 날을 또 놓친다 | `checkPick` |
| 오늘은 오늘 할 일이 남아 있을 때만 받음 | 다 끝낸 날에 잠금이 다시 걸리지 않게 | `canReceive` |
| 매주 반복 목표는 옮기지 않고 다음 회차를 그대로 | 운동·회화는 몰아서 하는 것이 의미 없다 | `spread`, AI 지시 |
| 대가 설명은 코드가 씀 | AI가 대가를 줄여 말하지 않게 | `describePick` |
| 같은 날은 한 번만 정리 | 두 번 눌러도 사본이 두 번 생기지 않게 | DB 고유 인덱스 `adjustments_recover_once` |

### 기존 "조정"과 무엇이 다른가

| | 조정 (있던 기능) | 놓친 날 이어 가기 (이번) |
|---|---|---|
| 계기 | 오늘이 버거울 때, 사용자가 먼저 말함 | 지난 날을 놓쳤을 때, 앱이 먼저 알림 |
| 다루는 일 | 오늘 남은 할 일 | 지난 3일 동안 인증하지 못한 할 일 |
| AI의 일 | 오늘 할 일을 줄이는 안과 대가 | 놓친 것 중 무엇을 살리고 어디에 넣을지 |
| AI가 없으면 | 조정할 수 없음 | 코드가 만든 기본안으로 정리 |
| 기록 | 남은 것을 끝내면 "조정" | 옮긴 사본을 모두 인증해야 "조정", 7일에 한 번 |

### 기존 기능과 충돌하지 않게 한 것

- 지난 날의 계획을 지우거나 바꾸지 않습니다. 기록 화면, 달력, 인증 기록은 예전과 같은 자료를 봅니다.
- 옮긴 사본은 보통 할 일과 같은 모양이라 오늘 목록, 인증, 잠금이 따로 고칠 것 없이 그대로 다룹니다. 새 칸은 `carried`(원래 날짜와 id) 하나입니다.
- DB 변경 전에도 앱이 돕니다. 새 칸이 없으면 오늘 화면의 줄을 숨기고, 기록은 예전 방식으로 셉니다.

### 실패와 빈 상태

| 상황 | 화면 |
|---|---|
| 놓친 일이 없음 | 오늘 화면에 줄이 없음. 주소로 직접 들어오면 "지금은 정리할 놓친 일이 없어요" |
| AI가 늦거나 실패함(25초, 재시도 없음) | "코치가 지금 답하지 못했어요. 기본 방법으로 정리할 수 있어요"와 기본안 |
| 하루 AI 횟수(3번)나 주간 금액을 다 씀 | 같은 안내와 기본안. 실패한 호출은 횟수에 세지 않음 |
| AI가 규칙에 어긋난 안을 냄 | 서버가 그 안을 버리고 나머지만 보여 줌 |
| 고르는 사이 계획이 바뀜 | "그사이 계획이 바뀌어 이 방법은 쓸 수 없어요" |
| 이미 정리한 날 | "이미 정리했어요" (DB 고유 인덱스로도 막음) |
| 기다리는 동안 | 코치 말풍선의 점 세 개, 버튼과 입력칸은 숨김 |

### 기술 선택

- **새 AI 호출 하나만 더했습니다.** 조정에서 쓰던 구조(구조화 응답 + zod, 사용량 3겹 제한, `ai_runs` 기록)를 그대로 쓰고, 목적 값 `recover`만 더했습니다.
- **AI는 "무엇을 살릴지"만 정합니다.** 날짜와 분량의 상한, 기록 규칙, 대가 설명은 코드가 정합니다. AI 답은 `lib/recover.ts`의 `checkPick`을 통과해야 화면에 나옵니다.
- **기본안을 먼저 둔 것은 의도한 단순화입니다.** 이 기능은 AI가 없어도 쓸 수 있어야 해서, 기본안은 단순한 규칙(가장 이른 빈 날부터 하나씩)으로 만들었습니다.
- **새 표를 만들지 않았습니다.** 정리 기록은 있던 `adjustments`에 `kind`, `for_date`, `repairs`, `source` 칸을 더해 남깁니다.

### 측정

정리 기록에 고른 안의 출처(`source`: 기본안 basic / 코치 안 coach)와 기록을 되살리는 정리인지(`repairs`)가 남습니다. 줄이 보인 횟수와 고른 안은 서버 로그(`recover row shown`, `recover chosen`)에도 남습니다. 테스터가 7명이라 결과는 "7명 중 몇 명이 정리했나" 같은 건수로만 봅니다.

### 확장 가능성

- 알림: 아침에 "어제 못 한 일이 있어요" 알림을 보내 같은 화면을 열게 할 수 있습니다(안드로이드 껍데기의 알림 기능 재사용).
- 계획 이어 짜기: 여러 날을 놓쳐 남은 기간이 모자라면, 남은 주의 흐름을 다시 짜는 것으로 넓힐 수 있습니다.
- 사용자가 늘면: 하루 상한(두 배)과 정리 기간(3일)은 `lib/recover.ts` 맨 위 상수 하나씩이라 테스트 결과에 따라 바로 바꿀 수 있습니다.

### 데모 순서

새 계정에는 지난 날이 없어서 바로 보이지 않습니다. 목표를 만들고 하루를 인증하지 않고 넘기면 다음 날 오늘 화면에 줄이 생깁니다. 자동 점검(`node scripts/e2e.mjs`의 [6])은 점검 계정의 계획에 지난 날짜를 넣어 이 흐름을 바로 돌리고, 화면 캡처를 로컬의 `design-preview/e2e/`에 남깁니다(저장소에는 올리지 않음).

### 알려진 한계

- 목표가 여럿일 때 한 목표의 계획 저장이 실패하면, 앞서 저장한 목표의 사본은 남고 정리 기록만 되돌립니다. 다시 고르면 그 목표에 사본이 한 번 더 생길 수 있습니다.
- 자정이 지나면 그날 할 일은 인증할 수 없습니다. 밤늦게 하는 사람은 "놓친 날"이 더 자주 생길 수 있습니다.

## 핵심 기능 명세

CRUD 대상은 **목표(goals)** 이고, 파일 업로드는 **목표 자료 사진**과 **인증 사진**으로 연결했습니다. 모든 데이터는 로그인한 사용자 본인만 읽고 쓸 수 있습니다.

### 사용자 흐름

가입(필수 동의 3가지) → 코치와 대화 → 알아들은 내용 확인 → 계획 생성 → 목표 화면(달력) → 오늘 할 일 → 시작(잠금) → 인증 → 잠금 해제. 버거운 날과 놓친 날은 코치 탭에서 상황에 맞는 대화를 고릅니다.

### 화면별 명세

| 화면 | 입력 | 사용자 행동 | 성공 결과 | 실패 결과 |
|---|---|---|---|---|
| 가입·로그인 `/login` | 이메일, 비밀번호, 필수 동의 3가지 / 구글·카카오 | 가입 또는 로그인 | 가입하면 첫 안내로, 로그인하면 오늘 화면으로 이동 | 동의 전에는 가입 버튼이 잠김. 틀린 정보는 안내 문구 |
| 첫 안내 `/start` | 없음 | "다음", "시작하기" | 실행을 돕는 연구 근거 네 장과 그것이 쓰이는 기능을 전체 화면으로 보여 준 뒤 코치 대화로. 대화 첫 화면이 "당신의 고민은 무엇인가요?"를 묻고, 말하면 그 자리에서 대화가 이어짐 | 건너뛰기(바로 대화로) |
| 코치와 대화(등록) `/goals/new` | 자유 대화, 선택지, 자료 사진(선택), 잠글 앱 | 목표와 사정을 말하고 "확인하러 가기" | 알아들은 내용을 확인 장에 채워 보여 줌. 대화는 이 기기에 저장돼 나갔다 와도 이어짐 | AI 응답 실패 시 안내 문구, 직접 적기로 넘어갈 수 있음 |
| 계획 확인(등록) | 목표, 기한 종류와 날짜, 가능한 시간, 하루 시간, 상황, 자료 사진, 잠글 앱 | "계획 만들기" | 저장 후 목표 화면으로 이동, 코치가 화면을 짚어 주는 첫 안내 | 항목별 오류 문구, 입력값 유지. 계획 생성 실패 시 목표는 저장하고 다시 시도 버튼 |
| 목록 `/goals` | 검색어, 종류 필터, 페이지 (5개씩, 목표가 6개 이상이면 검색 표시) | 목표 눌러 상세로 | 목표마다 D-day와 오늘 할 일 수 | 빈 상태 안내, 범위를 넘은 페이지는 마지막 페이지로 |
| 상세 `/goals/[id]` | 날짜 선택 | 달력에서 날짜를 눌러 그날 할 일 보기, 근거 화면으로, 수정·다시 만들기·삭제 | 달력, 고른 날의 할 일, 근거 요약 한 줄. 다시 만들어도 지난 날 계획과 기록은 그대로 | 없는 주소는 "목표를 찾을 수 없어요" 화면. 잠금 중에는 다시 만들기·삭제를 미리 막고 이유를 보여 줌 |
| 근거 `/goals/[id]/why` | 없음 | 주차를 펼쳐 보기 | 코치의 근거, 가정한 것, 주마다 하는 일, 알려 준 것 | 계획이 없거나 없는 주소면 없는 화면 |
| 수정 `/goals/[id]/edit` | 등록 확인 장과 같음 | "저장하고 계획 맞추기" | 저장 후 오늘 이후 계획을 다시 짬(오늘 인증한 것이 있으면 오늘도 그대로) | 등록과 같음. 잠금 중에는 저장을 막음 |
| 삭제 (상세의 확인 창) | 없음 | 휴지통 → "휴지통으로 옮기기" 또는 "그대로 두기" | 휴지통에 30일 두고 목록으로. 그 뒤 목표, 계획, 관련 사진을 지움 | 확인 창 안에 오류 문구 |
| 휴지통 `/goals/trash` | 없음 | 되살리기, 완전히 지우기(한 번 더 확인) | 지운 목표와 완전히 지워지기까지 남은 날 | 비었으면 빈 상태 |
| 오늘 `/today` | 없음 | 할 일 눌러 인증, "시작하기" | 위에서부터 목표 맥락 한 줄(D-day·주차·걸리는 시간), 잠금 상태와 인증한 수, 할 일, 이번 주 초점. 시작 전 확인 창(잠기는 곳, 바로 풀 수 없음, 조정의 대가, 사진 보관 기간) 후 잠금 | 쉬는 날, 조정으로 옮긴 날, 계획 기간이 끝난 날, 계획을 못 만든 목표를 각각 안내 |
| 인증 (오늘의 시트) | 사진(JPG·PNG·WEBP, 3MB 이하) / 퀴즈 답 / 40자 이상의 글 | 과제에 정해진 방식으로 인증 | AI가 판정과 이유를 돌려주고, 모두 통과하면 잠금 해제 | 통과하지 못하면 이유와 다시 인증, 판정 이의 제기 |
| 코치 `/coach` | 없음 | 상황에 맞는 대화 고르기 | 오늘 조정(남은 할 일이 있을 때), 놓친 날 이어 가기(있을 때), 새 목표 정하기 또는 하던 대화 이어 하기 | 고를 것이 없으면 그 줄을 흐리게 두고 이유를 적음 |
| 조정 `/goals/new?talk=adjust` | 사정 | 코치에게 말하고 조정안 고르기 | 조정안과 대가를 보고 고르면 오늘 할 일에 반영. 받는 날의 하루 분량을 넘는 안은 서버가 뺌 | "그대로 할게요" 선택 가능. 할 일을 오래 하지 않으면 오늘 화면 아래에 코치의 한마디가 뜸 |
| 내 정보 `/settings` | 잠글 앱과 그 화면 | 저장, 로그아웃, 탈퇴 | 다음 시작부터 적용. 탈퇴 시 모든 기록과 사진 삭제 | 탈퇴는 "탈퇴"라고 적어야 진행. 잠금 중에는 잠글 앱을 바꿀 수 없음 |

### 입력 규칙 (서버에서 다시 검사하고, DB 제약으로 한 번 더 막음)

| 항목 | 필수 | 규칙 |
|---|---|---|
| 목표 | 필수 | 1~40자 |
| 기한 종류 | 필수 | 정한 날까지(dated), 날짜 없이 완성(finish), 매주 반복(ongoing) |
| 날짜 | 정한 날까지일 때 필수 | 오늘 이후의 실제 날짜 |
| 하루 시간 | 필수 | 10~600분 |
| 가능한 시간 | 선택 | 120자 이하 |
| 지금 상황 | 선택 | 300자 이하 |
| 코치가 더 알게 된 것 | 선택 | 1,500자 이하 |
| 사진 | 선택 | JPG, PNG, WEBP, 3MB 이하 |

저장하는 동안에는 입력칸과 버튼을 잠가 중복 제출을 막습니다.

## 테이블 구조

Supabase(PostgreSQL)에 표 6개가 있고, 모든 표에 `user_id`와 행 단위 접근 제한(RLS)이 걸려 있어 본인 행만 읽고 씁니다. 전체 SQL은 [supabase/schema.sql](supabase/schema.sql)에 있습니다.

### goals: 목표와 AI가 만든 계획

| 컬럼 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `id` | uuid | 자동 | 기본 키 |
| `user_id` | uuid | 자동 | 주인 (auth.users) |
| `title` | text | 필수 | 목표, 1~40자 |
| `kind` | text | 필수 | dated / finish / ongoing |
| `deadline` | date | dated일 때 | 끝나는 날 |
| `daily_minutes` | integer | 필수 | 하루 시간, 10~600 |
| `schedule` | text | 선택 | 언제 할 수 있는지 |
| `note` | text | 선택 | 지금 상황 |
| `context` | text | 선택 | 대화에서 코치가 더 알게 된 사정 |
| `material_path` | text | 선택 | 자료 사진의 저장소 경로 |
| `material_summary` | text | 선택 | AI가 사진에서 읽은 내용 |
| `plan` | jsonb | 선택 | 계획 (요약, 근거, 가정, 주별 흐름, 날짜별 할 일과 인증 방식) |
| `plan_status` | text | 필수 | pending / ready / failed |
| `plan_generated_at` | timestamptz | 선택 | 계획을 만든 시각 |
| `created_at`, `updated_at` | timestamptz | 자동 | 만든·고친 시각 (트리거로 갱신) |

### 나머지 표

| 표 | 하는 일 | 주요 컬럼 |
|---|---|---|
| `proofs` | 인증 기록 (과제마다 가장 최근 한 건) | `goal_id`, `task_id`, `date`, `kind`(photo/quiz/write), `passed`, `reason`, `image_path`, `answer`, `appeal` |
| `app_settings` | 잠글 앱과 오늘의 잠금 상태 (사용자당 한 줄) | `lock_targets`(text[]), `lock_date` |
| `adjustments` | 계획 조정과 놓친 날 정리 기록 | `date`, `kind`(adjust/recover), `for_date`(정리한 지난 날), `repairs`, `source`, `reason`, `choice`, `impact` |
| `consents` | 약관·개인정보 동의 기록 | `version`, `agreed_at` |
| `ai_runs` | AI 사용 기록 (사용량 제한용) | `purpose`, `ok`, `model`, `input_tokens`, `output_tokens` |

사진은 Supabase Storage의 **비공개** 버킷 `goal-materials`에 `사용자 id/materials/` 또는 `사용자 id/proofs/` 경로로 저장하고, 화면에는 기한이 있는 서명 주소로 보여 줍니다. 인증 사진 원본은 판정 7일 뒤 지우고, 목표를 휴지통에서 완전히 지우거나(30일 뒤 또는 바로) 탈퇴하면 관련 사진을 함께 지웁니다.

계획이 끝난 목표: 모두 인증한 날짜 있는·완성 목표는 달성으로 보고 다음 계획을 묻지 않습니다. 일부만 인증한 채 끝났으면 목표와 계획을 그대로 두고 "다음 계획 받기"를 권합니다. 목표일까지 인증이 하나도 없으면 계획만 지우고 "목표일이 마감됐어요. 계획을 재조정할까요?"로 안내합니다. 매주 반복 목표는 기간이 끝나면 코치가 이어서 짤지 새로 짤지 묻습니다. DB는 `supabase/migrations/2026-11-16-trash-expire.sql`을 한 번 실행해야 합니다.

## 기술 스택

| 영역 | 쓰는 것 |
|---|---|
| 웹 앱 | Next.js 16 (App Router, Server Actions), React 19, TypeScript, zod |
| 데이터·로그인·파일 | Supabase (PostgreSQL + RLS, Auth, Storage) |
| AI | OpenAI 방식 SDK(`openai`)로 GPT 모델 호출. 응답 형식을 zod로 고정 |
| 배포 | Vercel (서울 지역) |
| 안드로이드 껍데기 | Java, WebView, 접근성 서비스(앱 잠금) |
| 점검 | playwright-core로 실제 브라우저(Edge)를 띄워 가입부터 탈퇴까지 자동 점검 |

데이터 변경과 AI 호출은 모두 서버(Server Actions)에서만 하고, 브라우저가 데이터베이스나 AI를 직접 부르지 않습니다.

## 실행 방법

1. 패키지를 설치합니다.

   ```bash
   npm install
   ```

2. Supabase 프로젝트를 만들고, SQL Editor에서 `supabase/schema.sql` 전체를 실행합니다. Authentication 설정에서 이메일 확인(Confirm email)은 꺼 둡니다. 이미 쓰던 DB라면 `supabase/migrations/`의 파일 가운데 아직 돌리지 않은 것만 날짜 순서로 실행합니다(놓친 날 이어 가기는 `2026-11-12-recover.sql`).
3. `.env.example`을 `.env.local`로 복사한 뒤 값을 채웁니다.
4. 개발 서버를 실행하고 `http://localhost:3000/login`을 엽니다.

   ```bash
   npm run dev
   ```

5. (선택) 자동 점검: 개발 서버를 3100번에서 띄운 뒤 실행합니다. 점검용 계정을 만들고 마지막에 탈퇴합니다.

   ```bash
   node scripts/e2e.mjs
   ```

## 환경 변수

| 이름 | 필수 | 설명 |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | 필수 | Supabase 프로젝트 주소 |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | 필수 | Supabase 공개 키 (예전 이름 anon). service_role 키는 쓰지 않습니다 |
| `OPENAI_API_KEY` | 필수 | AI 키 (서버에서만 씀) |
| `OPENAI_BASE_URL` | 선택 | 중계 서비스를 거칠 때의 주소 |
| `OPENAI_CHAT_MODEL`, `OPENAI_PLAN_MODEL`, `OPENAI_DAYS_MODEL`, `OPENAI_JUDGE_MODEL`, `OPENAI_PLAN_EFFORT` | 선택 | 용도별 모델과 계획의 생각 깊이 |
| `NEXT_PUBLIC_AUTH_PROVIDERS` | 선택 | 가입 화면에 보여 줄 소셜 로그인 (예: `google,kakao`) |
| `AI_BUDGET_USD`, `AI_USER_BUDGET_USD` | 선택 | 최근 7일 AI 예산, 전체와 한 사람 몫 (기본 70, 10달러) |
| `AI_PRICE_IN`, `AI_PRICE_OUT` | 선택 | 토큰 백만 개의 값 (기본 5, 20달러) |

로컬은 `.env.local`에, 배포는 Vercel의 Project Settings → Environment Variables에 같은 이름으로 넣습니다. 실제 값은 저장소에 올리지 않습니다.
